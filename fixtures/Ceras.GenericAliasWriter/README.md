# Historical writer — renamed open generics

`Ceras.GenericAliasWriter` holds the **v1** model of a save whose *generic* types have since been
renamed, and writes the byte-exact files that the cross-version tests in
`tests/Ceras.Test/Tests/RenamedGenericAliasTests.cs` (renamed types) and
`tests/Ceras.Test/Tests/GenericMemberOrderTests.cs` (a generic whose member order depends on its type
argument) load with the current model.

It is a separate project from `Ceras.HistoricalWriter` — and a separate set of golden files — for two
reasons:

- the v1 CLR types (`Legacy.*`) must be **absent from the reader build**, so
  `tests/Ceras.Test` does not reference this project and only ever sees the bytes plus the current
  model, exactly like the other historical fixtures;
- `Fixtures/HistoricalV1` is regenerated one change at a time, so extending it with a second,
  unrelated model would couple two changes.

Like the other historical writer it is built with the current toolchain and the current generator on
purpose: what makes these fixtures *historical* is the v1 CLR model and the v1 format written above it,
not an old language version.

**The checked-in bytes carry whatever robust format version the tree that generated them writes.** They
are regenerated by the command below whenever the format version changes, because a build reads its own
version only — a file written by an older experimental version is refused by name rather than
migrated. So a merge that lands on a different format version has to re-run the command (the output is
deterministic, so the diff is only the version and whatever else that version changed).

## Regenerating (only when intentionally updating a fixture)

```sh
dotnet run --project fixtures/Ceras.GenericAliasWriter -c Release -- --out tests/Ceras.Test/Fixtures/GenericAliasV1
```

The output is deterministic: the build timestamp is pinned to "unknown"
(`SetUnknownBuildTimestamp`), so re-running with unchanged inputs produces identical bytes (verified by
regenerating and comparing SHA-256). **Every byte in a diff is a real change to what old saves look
like.**

Ordinary CI never builds or runs this project; it only reads the checked-in files.

| Aspect | Fixture | v1 | Current |
| --- | --- | --- | --- |

| Renamed generic, second argument | `Save.bin` | `Legacy.Box`1<System.String>` | `Box<string>` |

| Overlapping names | `Save.bin` | `Legacy.Box`1<…>` **and** `Legacy.Box`1+Cell`1<…>` | `Box<int>` **and** `Box<int>.Cell<Coord>` — two definitions, not a prefix match |
| Generic nested in a renamed generic | `Save.bin` | `Legacy.Box`1+Cell`1<System.Int32,Legacy.Coord>` | `Box<int>.Cell<Coord>` |
| Renamed generic behind `object` | `Save.bin` | `Legacy.Box`1<System.Int32>` as a polymorphic type tag | `Box<int>` |
| Removed field inside a fixed-width struct | `Save.bin` | `Coord.X, Y, Z` | `Coord.X, Y` — exactly `Z`'s bytes skipped |
| Renamed members of a generic | `Save.bin` | `Box.Value`, `Crate.First/Second` | `Payload`, `Head`/`Tail` via `[PreviousName]` |
| Renamed generic as the save root | `TextBox.bin` | `Legacy.Box`1<System.String>` | `Box<string>` — the identity a wrong-root load is checked against |
| Collection of closures as the root | `IntBoxes.bin` | `List<Legacy.Box`1<System.Int32>>` | `List<Box<int>>` |
| Sentinel last | `Save.bin` | `Tail` | `Tail` — any desynchronisation before it is visible |
| Member order that depends on the type argument | `Wrap.bin` | `Legacy.Wrap\`1<Legacy.Coord>` written `Tag, Value` | `Wrap<Coord>` — the file's schema lists `Tag, Value`, which is what its bytes say |
| Added member of a generic | `Wrap.bin` | — | `Wrap<T>.Added` takes its declared default |

## The order-sensitive fixture, and what changed with it

`Legacy.Wrap<T>` is here because of a member-order defect, not about renaming: every closure of a
generic definition is written by the definition's one shared formatter, so `Wrap<Coord>`'s bytes are
`Tag` then `Value` (the parameter name sorts after `System.Int32`), while the *closure's* substituted
members sort the other way round (`Legacy.Coord` sorts before `System.Int32`). The per-closed schema
used to record the substituted order, so a file's schema did not describe its own bytes and a migration
read the wrong members. The schema now records the order the shared writer emits; `Format/LAYOUT.md`
has the rule and the reasoning.

What that correction changes, measured rather than assumed:

| | before | after |
| --- | --- | --- |
| payload bytes | — | **identical** for all four fixtures |
| schema section | substituted field order | written field order |
| layout fingerprint | — | changes for the closures whose two orders differ |
| a file written *before* the correction | records the substituted order | still misread - its own schema lies about its own bytes, and the order it was written in is recorded nowhere else in it |

The last row is the compatibility cost, and it is a silent one (a member reads its neighbour's value),
not a load failure. It is accepted: the robust format's compatibility promise starts with the next
documented format, and no golden fixture in this repository contains a user generic, so no checked-in
file changes behaviour.

The other generics here are deliberately minimal (**one member each**, apart from `Crate`, whose two
arguments sort the same way closed and open) so the *identity* problem they exist to pin is not
entangled with the order one.

## Changing a fixture

1. Change `V1Model.cs` (the old model).
2. Change the current model to match - `tests/Ceras.Test/Tests/RenamedGenericAliasTests.cs` for the
   renamed types, `GenericMemberOrderTests.cs` for `Wrap<T>`/`Sleeve` - keeping the
   `[PreviousTypeName]` / `[PreviousName]` aliases the migration needs.
3. Regenerate (command above) and review the byte diff.
4. Run `dotnet test tests/Ceras.Test`.
